# Proctoring: Violation Events, Sequence Numbers & Offline Buffer

## 1. Monotonic Sequence Numbers (`seq`)
Network delays and intermittent wireless drops can cause events to arrive at the backend out of order.
- Each event generated by `ProctorEngine` is tagged with a strictly monotonic integer: `seq = 1, 2, 3...`.
- The database enforces a unique composite constraint: `UNIQUE(attempt_id, seq)`.
- **Idempotency Guarantee**: If an unstable network causes the client to retry sending `seq = 2`, the backend detects the duplicate key and returns `HTTP 200` without incrementing strike counters twice.

---

## 2. Server-Authoritative Debounce & Grace Windows
To prevent a single user gesture (e.g. exiting fullscreen which also triggers a window blur) from multiplying into multiple strikes:
1. **Consecutive Tab-Switch Window (3.0s)**:
   Any `tab_switch` or `blur` event occurring within 3 seconds of a previous recorded strike is logged as a continuing observation rather than an additional strike.
2. **Fullscreen Return Grace Window (5.0s)**:
   When fullscreen is lost, the candidate has a 5-second grace window to restore fullscreen before the strike counter increments further.

---

## 3. Offline Buffer & Reconnection Queue
When an attempt is in progress and the user loses internet connection:
1. The `ProctorEngine` catches failed network requests and appends the violation to an in-memory & `localStorage` array.
2. A `window.addEventListener('online', ...)` listener immediately triggers `.flush()`, sending buffered events in sequential order once connectivity is restored.
3. The server validates that timestamps fall within the active exam window and catches up the attempt's audit log.
